## Rules exercised

- Feed records are read through SQLite `mode=ro`; the realtime DB is never modified by this package.
- Missing symbol/window, provisional/incomplete range, stale observation, open gap, conflict event, bad payload digest, bad SQLite, bad UTC grid or missing source provenance fail closed.
- Daily overlap compares exact symbol/interval/UTC key and decimal OHLCV. Identical overlap is `MATCH_IDEMPOTENT` and does not write another warehouse row. Mismatch is `CONFLICT`, preserving both sides. Missing realtime stays `MISSING_REALTIME` and only requests a separately authorized bounded recovery.
- Registry C is read and hash-verified. We return a content-addressed `PROPOSED_ONLY` record; no event, checkpoint, catalog or Registry snapshot is written.
- Before a proposal, the adapter re-runs the requested interval/window/cutoff through the pinned native `HistoricalWarehouse.query(..., include_registry=True)` against the supplied read-only warehouse root. It requires exact equality for every normalized bar and the complete Registry snapshot; detached caller-provided rows, receipt pins, or re-sealed context substitutions fail closed as `DAILY_NATIVE_READBACK_MISMATCH`. The native Registry query verifies retained ZIPs, source receipts, and physical shard rows. This is integrity validation under the repository's local trust model, not independent publisher-origin attestation.
- Streaming bars remain `FORWARD_UNQUALIFIED`; Binance Vision history remains `RETROSPECTIVE_NON_PIT`. The adapter cannot promote source authenticity, PIT/OOS eligibility, alpha, Paper or live execution.
- The production adapter has no writer. Test code alone copies generated fixtures from pytest temporary storage into a disposable ResearchBarStore.

## Audit remediation status

The producer now writes a versioned, forward-only normalized-row receipt in the same SQLite transaction as each newly inserted final bar. It binds provider/market/symbol/interval, UTC identity, availability/finality, exact OHLCV/trade count, event digest, replay identity, normalized-row digest, producer identity, and the producer source-code SHA-256. Duplicate finalized rows do not rewrite receipts; old rows are never backfilled. The consumer adapter requires an externally supplied expected producer code pin and blocks missing or altered receipts. This is a local producer attestation: raw event bytes are not retained, and the receipt is neither a Binance signature nor proof of provider rights or tamper resistance against a writer able to rewrite both the database and code pin. Generated-fixture helpers remain isolated to temporary test storage.

Projected rows are revalidated against the pinned native canonical seal, schema, source class, UTC identity/window, finality availability, constituent count and member digests before any reconciliation result is produced. Reconciliation carries both exact sealed rows and is recomputed before Registry proposal generation. A proposal requires the original daily query context and the matching sealed Registry snapshot; it checks the query window, exact row membership, archive key/receipt, covered window, gaps, and conflicts. Status-only or one-sided evidence cannot create a false positive proposal.

All feed integrity reads execute inside one explicit SQLite read transaction. The gap query now requires the selected `reason` column. Concurrency regression coordinates a commit between reader steps and verifies the reader sees a single pre-commit snapshot; the next read sees the committed gap.

The generated archive ZIP fixture includes variable ZIP metadata, so per-job source/proposal hashes may differ. Each artifact reports its own hash and marks this variation; hashes are not claimed as cross-run reproducible. CI provenance separates the tested merge checkout SHA from the exact PR head. The job now imports the read-only allowlisted live-report projection from pinned #331 and checks that its output contains only the watchdog's eight sanitized fields; this is generated synthetic evidence, not a host report or MCP deployment. A separate generated-fixture profile measures elapsed time, Python peak allocation, decoded logical bytes, SQLite file-size proxy, and read-snapshot duration for 1/100/1,000 rows. Proposed bounds are 10,080 rows, a 5-second adapter query budget, 30 seconds total per profiling window, and 128 MiB Python peak allocation. The SQLite standard library exposes no physical bytes-read counter here, so physical disk I/O is explicitly not measured and host resource/capacity gates remain pending.

CI installs `pytest-timeout==2.4.0` and passes `--timeout=60`; timeout enforcement is enabled for each test. Any pytest timeout remains a test failure.

## Recovery lineage and 24-hour evidence closure (F5/F6)

REST gap recovery writes a separate `atlas.realtime-market-feed.rest-backfill-attestation.v1` receipt in the same SQLite transaction as each newly recovered bar. The receipt identifies `BINANCE_SPOT_PUBLIC_REST_MARKET_DATA`, the REST recovery producer and its code SHA-256, the exact kline request/window, normalized row and response-row/batch digests, finality, UTC identity and actual local availability time. It does not claim a Binance signature. Existing rows are never retroactively attested; if a matching legacy row has no valid receipt, the transaction rolls back and the gap stays open. A gap closes only after bar content and every receipt seal read back successfully.

The adapter requires both the WS producer pin and, for a REST-sourced row, the separate REST producer pin (`expected_rest_producer_code_sha256`). Mixed WS/REST windows are supported only when both pins are supplied. A stored REST receipt with a missing/wrong code pin, invalid request range, altered OHLCV, missing lineage, malformed seal or conflicting prior bar remains blocked.

Service events now carry `run_id` and a monotonic timestamp. A run also binds the exact source, normalized symbol set, duration, configuration hash, UTC start/stop and monotonic start/stop. New rows with valid lineage emit run-scoped `FINAL_BAR_RECEIVED` events. Reopening a prior run can emit `RESTART_REPLAY_VERIFIED` only after SQLite integrity and each requested symbol's latest persisted bar/lineage have been independently read and matched.

The normal `--report` remains a short, latest-state diagnostic; it deliberately cannot pass the 24-hour evaluator. Build a complete, versioned, read-only evidence envelope for a specific closed run with:

```powershell
python -B -m tools.realtime_market_feed.observation_evidence --database "E:\\path\\market-feed.sqlite" --run-id "<exact-run-id>" --output "E:\\path\\observation-evidence.json"
```

The separate verifier reopens the exact database read-only, runs `PRAGMA quick_check`, exports the full run-scoped event set (not a recent-events tail), checks event IDs and clocks, computes expected closed-minute coverage per symbol, verifies lineage-seal presence, open gaps, conflicts, latest trade/quote freshness and later receipts after faults, and binds the report to database/WAL digests and the verifier code pin. The acceptance evaluator also reopens the supplied database and recomputes the entire envelope; a JSON report, status field or recomputed digest alone cannot pass. If the database is unavailable, truncated, changed during verification, or the verifier pin differs, the result is blocked. This local check is not a cryptographic defense against a hostile user with write access to both the database and verifier; no exchange signature or external custody is claimed.

The observation gate requires exact run/source/config/symbol/code pins, at least 86,400,000 ms on both UTC and monotonic clocks, bounded bracket skew, complete run-scoped events, planned-rotation→later-connection causality, every expected closed minute and receipt lineage, no open gaps/conflicts/missing bars, fresh latest market state, and restart/replay verification. Natural faults are derived from events: an unrecovered fault blocks; a recovered socket fault must be followed by a later connection, a rejected message by a later sealed final-bar receipt, and a backfill fault by a completed backfill event. `NOT_OBSERVED` remains distinct from a recovered-fault result. Unknown fields/event types, mismatched run IDs, duplicated/reordered events, impossible timestamps, truncation and source/database disagreement block.

These gates and the F5 tests use disposable generated fixtures and injected REST responses only. They do not create a new network request, perform a live capture, access the owner's runtime/database, change the Daily warehouse, or certify the original 24-hour trial. The original trial remains `24H_RESULT_PENDING` until its genuine final database/report and original code/config/run contract are supplied.
