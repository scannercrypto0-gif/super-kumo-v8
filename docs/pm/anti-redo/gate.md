# ATLAS pre-assignment reuse gate

Provisional Owner B, Issue #205 comment 6824875424. PM owns disposition before assigning Work, Codex or another manager. Review artifacts are versioned with the architecture draft. A documented disposition conveys no new execution, coding, data, trading, merge or G0 authority.

## Inputs and decision order

1. Record task, affected capability IDs, exact existing PR/owner, current main and relevant head/base pins. Attach lookups over the coverage index, code paths, symbols, stacked branches and prior Work/Audit. Cite the last actual Owner handoff and later applicable decisions. Record exclusion and uncertainty explicitly.
2. Review the old/current crosswalk at those pins. State the changed seam, path/contract, observable failure and smallest remedy. Unchanged accepted scope resolves to `ALREADY_COVERED`. Existing disconnected code resolves to `CONNECT_EXISTING` with `REUSE_WITH_ADAPTER` only if the contract delta is proven. Missing inventory or stale pins resolve to `INVENTORY_REQUIRED`. A parallel build with unresolved overlap resolves to `BLOCKED_DUPLICATE_RISK`.
3. A proved `REAL_GAP` can proceed to approval. Identify accountable role, required decision, current scope authority, and rollback. An approval-only finding grants no runtime action. Evidence-only gaps belong to custody and review first.
4. For every accepted test used, cite ledger ID and compare exact source/test/workflow, fixture, environment, authority and result scope. If a prior test is proposed again, require a changed pin or assumption, a reproduced failure, or demonstrated missing coverage. Record the affected assertion and minimal new case. Unknown test identity or scope cannot be promoted. A path match, title match or common blob alone cannot prove semantic duplication.
5. PM signs disposition at exact task revision and pins. Component owner signs the overlap determination. Audit independently reviews the changed evidence scope when the task's authority requires it. Refresh on new commit, changed fixture/contract, policy change, expiry, or superseding decision. In a stale/unknown state, hold assignment.

## Proposed GitHub integration

Use a PR template that links the versioned pre-assignment record and its decision; use the same record for non-PR work on #205. A future read-only check should validate against `gate.schema.json`, resolve IDs and exact pins, detect historical paths/symbol overlap and test intersections, and confirm a human review reference. The check should reject missing fields, unknown IDs, stale pins, unjustified reruns, unreviewed overlap, and unauthorized scopes. Check failure should link the precise missing field or conflicting capability. Once separately approved, register a single required check on protected target branches using stable check naming; use consistent results for docs-only PRs and avoid ambiguous duplicate workflow check names. PM should gate assignment itself before any branch protection runs.

A false positive requires a scoped, time-bounded reviewer decision that identifies the overlap and proves the differing contract or assertion. Record the approving PM, component owner, reason, exception scope, expiry and pinned revision. Revalidate on pin changes. Exception review cannot bypass source rights, trading, G0 or independent approval controls. Rollback is to revoke the assignment record and withdraw the scoped proposal; keep all evidence and commit history. Enforcement code and changes to repository protection require separate Owner authority.

## Executable remediation candidate

The previous candidate check is superseded by the split workflow in this draft. **Deployment status: ENFORCEMENT_BLOCKED.** Candidate CI runs adversarial fixtures with a read-only token on the PR head. It provides test evidence only. The separate trusted validator is designed for a `pull_request_target` invocation from the approved base, with base workflow and checkout SHA equality. It fetches the PR head as Git objects, never checks out or executes proposed code, and reads policy from the pinned base Git tree. Missing policy, permission, review, run, object or other required input blocks.

### Trusted policy and authenticated assignment

Deployment requires an independently reviewed `.github/anti-redo-policy.json` on the approved base. It is intentionally absent from this draft. The base policy fields are `version: 2`, `repository`, `base_ref`, `pm_ids` (GitHub numeric user IDs), `capabilities` (ID → `head_sha`, `ref` such as `heads/main`, `owner_ids`, and `contracts`), `evidence`, and `pure_docs` (exact reviewed Markdown path → Git blob ID). Policy, workflows, validators, tests and the PM register require assignments. Other documents are sensitive unless their exact regular-file blob and path were reviewed and listed in trusted policy. Deletions and both sides of renames remain covered.

The PM's GitHub **APPROVE** review on the exact head carries a first line of `ATLAS-ANTI-REDO-V2` followed by JSON. Its fields are `revision` (repository, PR number in `pr`, base ref, base SHA and head SHA), `records`, and `manifest_id`, the SHA-256 of the sorted compact ASCII JSON with that field omitted. Each record carries the existing task rationale, lookups, continuity, authority and rollback fields, plus `paths`, `capability_ids`, `contract_ids`, `head_pins`, `tests_reused`, `evidence` and `new_tests`. The component owner's separate exact-head GitHub **APPROVE** review body is `ATLAS-COMPONENT-V2 <manifest_id> <task>`. This places exact-head approval outside the commit being approved and binds it to the reviewed manifest. Free-text names or references do not grant signoff. An override must carry a non-empty reason, UTC expiry in the future and exact scope (revision, task, paths, capabilities and contracts). It does not bypass authentication, evidence verification or complete path coverage.

Each trusted evidence entry records `source_sha`, `runner`, `run_id`, `job_id`, `run_url`, `workflow_path`, `job_name`, `labels`, and `objects` (source/test/workflow/fixture groups with path-to-blob IDs). The validator reconciles the submitted ID and exact metadata to the base ledger, verifies the Actions job/run metadata and compares declared blobs at the tested commit and PR head. Policy reviewers must account for transitive code, runner and fixture dependencies before accepting a ledger entry. Missing evidence results in an inventory hold. Candidate tests mock the authenticated API; they do not constitute an operational approval or protected-check test.

After separate authorization, an administrator must deploy the base policy and validator and arrange an independently controlled required check bound to the exact PR head. A `pull_request_target` workflow result alone is insufficient to demonstrate that binding or required enforcement. Review events do not automatically re-run the trusted workflow; the trusted integration must refresh evaluation on reviewer, head or base changes. Confirm negative cases on a protected test branch before enabling protection on main. Until then the manual PM gate remains mandatory. This draft changes neither branch protection nor runtime authority.
